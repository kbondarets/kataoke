# kataoke — правила проекта

Правила — не пожелания, а критерий приёмки. Ревьювер проверяет **против этого
файла**, а не против своего вкуса. Если правило мешает — его меняют осознанно,
а не игнорируют.

Источник истины по продукту — `VISION.md`. Правило, противоречащее `VISION.md`, —
повод обновить `VISION.md`, а не молча его обойти.

---

## 1. Что читать

- **Всегда:** `VISION.md` (замысел), `.clinerules/rules.md` (короткие правила),
  `STATE.md` (текущий статус), этот файл.
- **При выборе задачи:** `VISION.md` §12 (план по этапам).
- **При спорах об архитектуре:** `VISION.md` §4 (архитектура) и §14 (открытые вопросы).
- **Никогда целиком:** `node_modules/`, `dist/`, `package-lock.json`.

## 2. Язык

- **Всё, что видит пользователь, — по-русски.** Кнопки, ошибки, подсказки,
  пустые состояния.
- **Ответы владельцу — по-русски.**
- **Документация — по-русски** (проект начат по-русски; консистентность важнее
  внешних конвенций).
- **Комментарии в коде — по-русски** и объясняют *почему*, а не «что делает код».
- **Идентификаторы — на английском** (`getPositionSec`, `parseLrc`,
  `YandexMusicAdapter`).
- Ошибки короткие и человеческие: «Текст для этого трека не найден.», а не
  `lyrics_not_found_error_v2`.

## 3. Границы модулей (главное правило проекта)

Правка в одном модуле не должна требовать правки в другом.

| Слой | Можно | Нельзя |
| --- | --- | --- |
| `src/core` | типы, sync engine, разбор LRC, чистая логика | знать про конкретный сервис или DOM-селектор |
| `src/adapters/<service>` | DOM-селекторы, доступ к медиа-элементу, метаданные трека | импортироваться из `core`, `ui`, `providers` |
| `src/providers/<name>` | сетевые запросы, разбор ответа одного источника | знать про адаптеры и UI |
| `src/ui` | компоненты Preact, стили, рендер в Shadow DOM | знать DOM-селекторы сайта, звать провайдеров напрямую |
| `src/background` | service worker, сообщения, разрешения | содержать логику UI |
| `src/content` | bootstrap: выбрать адаптер, запустить движок, смонтировать оверлей | содержать бизнес-правила, которым место в `core` |
| `shared` (если появится) | общие типы, чистые помощники | зависеть от DOM или Node |

Проверка на ревью: «если вёрстка Яндекс Музыки поменяется, сколько файлов чинить?»
Правильный ответ — один.

## 4. Один файл — одна ответственность

- Файл больше **250 строк** — причина разбить. Больше **400** — блокирующее
  замечание.
- Компонент Preact — один экран или один переиспользуемый элемент.
- Имя файла говорит, что внутри: `parse-lrc.ts`, `sync-engine.ts`, `overlay.tsx`.
- Имена: `kebab-case.ts`, `PascalCase.tsx` для компонентов.

## 5. TypeScript

- `strict: true`, `noUncheckedIndexedAccess: true`. Никаких обходов через `any`.
- `unknown` вместо `any` для внешних данных: сначала проверка, потом использование.
- Именованные экспорты. `export default` — только для экранных компонентов Preact.
- Без `enum` — `as const` + union-типы.
- Единицы времени: адаптеры отдают **секунды** (`timeSec`), парсер LRC работает
  в **миллисекундах** (`offsetMs`). Единица обязана быть в имени.


## 6. Sync engine (ядро продукта)

- Позиция берётся только из медиа-элемента. Прогресс-бар в DOM — не источник истины.
- Между опросами `currentTime` позиция **интерполируется** через `performance.now()`
  и `playbackRate`; опираться на один `currentTime` нельзя.
- Обрабатывать `play`, `pause`, `seek`, `ratechange`, `ended`, смену трека.
- Рендер — по `requestAnimationFrame`, но перерисовка только при смене активной
  строки или слова.
- Движок обязан тестироваться **без браузера**: подать позицию и таймлайн —
  получить активную строку.

## 7. Оверлей (ядро продукта)

- Рендер в Shadow DOM, никакой протечки стилей в обе стороны.
- Пересчёт позиции при ресайзе, скролле и SPA-навигации
  (`MutationObserver` + перехват `history.pushState`/`replaceState`).
- CSS сайта не меняет наш вид; наш CSS не меняет страницу.
- Оверлей переживает смену трека без размонтирования.

## 8. Сеть и сбои

- У каждого внешнего запроса есть **таймаут**. Запрос без таймаута — блокирующее
  замечание.
- Любой сетевой сбой превращается в понятное состояние на русском
  (например, «Не удалось получить текст. Проверьте соединение.»).
- Оверлей никогда не остаётся в бесконечной загрузке.
- Результаты кешируются (`chrome.storage`) по ключу `трек + длительность`, чтобы
  не запрашивать один трек дважды.
- Историю прослушивания не логировать никуда, кроме локального хранилища.

## 9. Разрешения и приватность

- Разрешения MV3 минимальны: только домены, которые реально поддерживаем.
- Аналитики в MVP нет.
- Секретов в бандле нет. Ключи (если когда-либо появятся) — только через `.env`
  и `.gitignore`.
- Мы не читаем содержимое страницы сверх того, что нужно, чтобы найти плеер и
  текущий трек.

## 10. Что мы не делаем

- Удаление вокала / караоке-микс на DRM-сервисах — см. `VISION.md` §6.1.
- ML-модели в клиенте — см. `VISION.md` §5.1.
- Сервер в MVP — см. `VISION.md` §9.
- Аккаунты, синхронизация между устройствами, интерфейс не на русском в MVP —
  см. `VISION.md` §6.2.

PR, добавляющий что-то из этого списка, отклоняется со ссылкой на `VISION.md`.
Если владелец решил иначе — сначала обновляется `VISION.md`.


## 11. Тесты

- Тест — это код проекта, а не «скрипт, чтобы посмотреть».
- Приоритет: (1) чистая логика в `core` (парсер LRC, sync engine, матчинг треков);
  (2) разбор ответов провайдеров; (3) UI — только там, где логика живёт в компоненте.
- Новая функциональность без теста не принимается. Исправленный баг приходит с
  тестом, который его ловит.
- Тесты не ходят в сеть. Только моки.
- Тест, который всегда зелёный (нет `assert` или проверяет константу), хуже, чем
  отсутствие теста.

## 12. Git

- `main` — всегда рабочая версия. Прямых коммитов в `main` нет.
- Ветка: `feature/<имя>`, `fix/<имя>` или `chore/<имя>` от `main`.
- Коммит: `<тип>: <описание>`. Типы: `feat`, `fix`, `docs`, `refactor`, `test`,
  `chore`, `merge`.
- Слияние — только после `npm run check` и ревью.

## 13. Ревью

- Ревью делает **отдельный агент** (`agents/reviewer.md`) по
  `.clinerules/workflows/review.md`. Автор себя не ревьюит.
- Ревьюер проверяет **pull request / merge request** — процедура в workflow.
- Ревьюер не правит код: находит и описывает, правит автор.
- Формат вердикта задан в workflow и не импровизируется.

## 14. Документация после задачи

- `STATE.md`: статус, последняя задача, новые подводные камни. Блок «Последняя
  задача» **перезаписывать**, а не накапливать — история живёт в `git log`.
- `VISION.md`: только если изменилось продуктовое решение (тогда это осознанная
  правка, согласованная с владельцем).
- `README.md`: только если изменилось поведение для пользователя.

## 15. Чек-лист перед «готово»

- [ ] Задача сделана в отдельной ветке.
- [ ] `npm run typecheck` — без ошибок.
- [ ] `npm test` — все тесты проходят.
- [ ] `npm run build` — собирается.
- [ ] Границы модулей не нарушены (раздел 3).
- [ ] Новые тексты для пользователя — на русском.
- [ ] Оверлей в Shadow DOM и не протекает стилями.
- [ ] Позиция берётся из медиа-элемента, а не из прогресс-бара.
- [ ] Нет обхода DRM, нет модификации аудио.
- [ ] У новых сетевых вызовов есть таймаут.
- [ ] Тест на новое поведение написан.
- [ ] Ревью агентом-ревьювером пройдено, блокирующих нет.
- [ ] Резюме на русском: что сделано, где, как проверено, что осталось.


## 16. Эффективность агента

Токены — ограниченный ресурс. Каждое действие должно двигать задачу вперёд.

### 16.1. «Лазер, а не дробовик»

- Читать только файлы, нужные на текущем шаге: не больше 2–3 за шаг.
- Не сканировать репозиторий (`Get-ChildItem -Recurse`, `grep -r`), если область
  задачи известна. Для навигации — карта ниже.

Карта репозитория:

```
kataoke/
  VISION.md              # замысел продукта (источник истины)
  README.md              # точка входа для человека
  AGENTS.md              # стек и конвенции кода
  STATE.md               # текущий статус, последняя задача, подводные камни
  projectRules.md        # этот файл
  .clinerules/
    rules.md             # короткие правила
    workflows/
      review.md          # процедура ревьювера и формат вердикта
      feature.md         # процедура разработчика (ветка → код → проверки → PR)
  agents/
    frontend-architect.md
    backend-architect.md
    reviewer.md
  skills/
    <скилл>/SKILL.md
  src/
    core/                # sync engine, LRC, типы
    adapters/            # адаптеры сервисов
    providers/           # источники текстов
    ui/                  # оверлей Preact, popup
    background/          # service worker
    content/             # bootstrap content script
```

### 16.2. Отладка

- Когда тест падает, сначала читать полный текст ошибки и относящуюся к нему
  часть теста. Не гадать о внутренностях.
- **Максимум 2 попытки** исправить одну и ту же ошибку. После второй — стоп и
  отчёт владельцу: что пробовал и какая ошибка осталась.
- Запрещено: временные скрипты (`tmp-*.ts`, `check-*.ps1`) для проверки гипотез
  о коде, который можно прочитать или проверить стандартным выводом.

### 16.3. Дисциплина шага

- Перед открытием файлов или написанием кода: перечислить файлы (макс 3), план
  из 3–4 пунктов, допущения и вопросы.
- Если в задаче есть двусмысленность, которая может изменить результат, —
  спросить, а не гадать.
- Не больше 3 команд терминала подряд без промежуточного отчёта.

### 16.4. Экономия контекста

- Не переписывать в ответ содержимое прочитанных файлов — ссылаться по имени.
- Рассуждения длиннее 5 строк — только по просьбе владельца.
