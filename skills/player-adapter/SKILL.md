# Скилл: адаптер сервиса

## Когда нужен

- Добавление нового сервиса (Spotify, YouTube Music).
- Починка Яндекс Музыки или YouTube после редизайна.
- Вопрос «как понять, что сейчас играет».

## Контракт (из `VISION.md` §4.2)

```ts
interface PlayerAdapter {
  id: string;
  matches(url: string): boolean;
  getTrack(): TrackInfo | null;
  getPositionSec(): number | null;
  isPlaying(): boolean;
  getPlaybackRate(): number;
  on(event: PlayerEvent, cb: () => void): () => void;
  destroy(): void;
}
```

`TrackInfo`: `title`, `artist`, `album?`, `durationSec`, `sourceId?`.
`getPositionSec()` отдаёт **секунды**.

Реализация адаптера **не** содержит синхронизации — только «что сейчас», «где
мы во времени», «что происходит».

## Правило изоляции

Любой селектор сервиса живёт в одном файле (или одной папке) адаптера. Ни
`core`, ни `ui`, ни `providers` не должны знать про `.deco-player` или `#movie_player`.

Проверка: «если вёрстка сервиса поменялась — сколько файлов править?» — один.

## Порядок исследования сервиса

1. Открыть сервис в браузере, воспроизвести трек.
2. Найти медиа-элемент: DevTools → Elements → поиск `<video` / `<audio`.
   Признак: у него меняется `currentTime`, работает `duration`.
3. Понять, где трек-метаданные: в DOM (заголовок плеера), в `document.title`,
   в URL, в атрибутах `<meta>`, в JSON-снапшоте в HTML.
4. Проверить поведение в SPA: переключение трека не меняет URL или меняет частично.
5. Записать для себя хрупкость каждого источника и наметить резервный.

## Источники метаданных (по убыванию надёжности)

| Источник | Плюсы | Риски |
|---|---|---|
| Media Element / MediaSession (`navigator.mediaSession.metadata`) | стандартизировано, есть во многих сервисах | не все сервисы заполняют |
| `document.title` | часто содержит «Трек — Артист» | формат меняется, есть уведомления |
| Явные DOM-узлы в плеере | точные данные | ломаются при редизайне |
| URL (`/album/123/track/456`) | стабилен для навигации | не всегда содержит название |
| JSON в странице | максимум информации | неофициально, может ломаться |

Для Яндекс Музыки в первую очередь стоит проверить `navigator.mediaSession` и
`document.title`: публичного стабильного API у сервиса нет, DOM-зависимость —
основной риск (`VISION.md` §9.1).

## Устойчивость к изменениям

- Один селектор — один селектор: не «цепочка из пяти классов», а поиск по
  семантике (атрибут, роль, текстовый паттерн) там, где возможно.
- Несколько стратегий поиска по очереди (fallback-цепочка) — лучше, чем один
  хрупкий путь.
- Если ничего не нашли — не падать молча: вернуть `null` и отдать наверх
  состояние «сервис не распознан».
- Периодически перепроверять, что трек не сменился «тихо».

## SPA и смена трека

- Слушать `loadstart` и `loadedmetadata` на медиа-элементе.
- Плюс `MutationObserver` на контейнер плеера.
- Плюс перехват `history.pushState`/`replaceState` и `popstate`.
- Событие `trackchange` отправлять только **при реальном изменении**
  `trackId`/названия+артиста, чтобы не перезапускать всё на каждый мутация-чих.

## Позиция

- `currentTime` медиа-элемента — единственный источник.
- Если на странице несколько `<video>`/`<audio>` (например, реклама), выбираем
  тот, который «играет» и находится в контейнере плеера, а не в баннере.
- `playbackRate` — опрашивать и/или слушать `ratechange`.

## Тестируемость

Адаптер — самая «грязная» часть: DOM. Поэтому:

- Логику матчинга URL и нормализации метаданных — вынести в чистые функции,
  тестировать без DOM.
- DOM-доступ — тонкий слой поверх чистых функций.
- В тестах можно поднимать jsdom и подавать фрагменты DOM.

## Анти-паттерны

- Адаптер сам запускает таймеры синхронизации и рендера.
- Адаптер импортирует UI.
- Адаптер импортируется из `core`.
- Магическое число вместо `duration` из медиа-элемента.
- Поиск плеера через `document.querySelector` на каждом кадре — кешировать
  ссылку и перепроверять только по событиям.
- `innerHTML` в чужой контейнер (ломает сайт).
