# Скилл: разбор LRC

## Когда нужен

- Парсинг ответа LRCLIB (`syncedLyrics` / `plainLyrics`).
- Преобразование текста в таймлайн для sync engine.
- Отладка «строка подсвечивается не там».

## Форматы, которые надо понимать

### 1. Plain text

```
Просто текст
Без каких-либо таймингов
```
Синхронизировать нечем. Показываем как есть, без подсветки по времени.

### 2. Line-sync LRC

```
[ar:Ария]
[ti:Беспечный ангел]
[al:Генератор зла]
[offset:+250]
[00:12.34]Первый куплет
[00:18.10]Вторая строка
[01:02.00][02:15.00]Припев одинаковый
```

- Метка `[mm:ss.xx]` — минуты, секунды, сотые (иногда тысячные `[mm:ss.xxx]`).
- В одной строке может быть **несколько** меток — строка повторяется в каждом
  указанном месте. Это частый пропуск в реализациях.
- `[offset:±N]` — поправка в миллисекундах: **прибавляется** к каждому времени;
  по спецификации — тег до первой метки, но на практике встречается и в середине.
- Время в префиксе файла (метаданные) не путать с меткой времени.

### 3. Word-sync LRC (k-word, расширение)

```
[00:12.34]<00:12.34>Первое <00:12.90>слово <00:13.40>строки
[00:18.10]<00:18.10>Вторая <00:18.70>строка
```

- Метка `<mm:ss.xx>` внутри строки — время начала слова.
- Если у слова нет метки — оно продолжает предыдущее, моменты разбиения неизвестны.
- Бывают `<>` с абсолютным временем (как выше) и реже — с относительным. Если
  значения внутри фигурных скобок ведут себя как дельты — обрабатывать как дельту
  от начала строки, но такой формат встречается редко: **сначала предположить
  абсолютное**, и только при явных признаках (монотонность нарушена) — дельты.

## Краевые случаи (каждый должен быть покрыт тестом)

| Случай | Ожидаемое поведение |
|---|---|
| Пустая строка между куплетами | Сохранить как разделитель (или пропустить, но не сдвигать следующие) |
| Несколько меток перед текстом | Одна «логическая» строка, но N позиций в таймлайне |
| `[mm:ss]` без долей | `.00` |
| `[mm:ss.xxx]` (миллисекунды) | Обработать как миллисекунды, не как сотые |
| `[offset:-500]` | Вычитать 500 мс из всех времён |
| Не-монотонные метки | Не падать; сортировать и логировать (в проде — не ломать UI) |
| Отрицательное время после offset | Обрезать до 0 |
| BOM в начале файла | Не ломать первую строку |
| `\r\n` | Нормализовать |
| Метаданные без тайминга (`[ar:...]`) | Не попадать в таймлайн как строка |
| Текст на нескольких языках, эмодзи | Не ломать разбиение на слова (эмодзи — не отдельное «слово» подсветки) |

## Тип результата (ориентир)

```ts
type TimedWord = { text: string; startMs: number; endMs?: number };
type TimedLine = { text: string; startMs: number; endMs?: number; words?: TimedWord[] };
type LyricsTimeline = { kind: 'plain' | 'line' | 'word'; lines: TimedLine[] };
```

- Парсер работает в **миллисекундах**.
- Наружу (в адаптеры и UI) время отдаётся в **секундах**: конвертация на границе.
- `endMs` строки может быть неизвестен — тогда вычисляется как `startMs`
  следующей строки (или `duration` трека для последней).

## Алгоритмические тонкости

- **Поиск активной строки**: бинарный поиск по `startMs`, не линейный перебор на
  каждом кадре.
- **Активное слово**: внутри найденной строки — бинарный поиск по словам.
- Прибавление `offset` делать **один раз** в парсере, не в движке: иначе смещение
  или удвоится, или потеряется на перемотке.
- Сохранять исходный текст строки для рендера; `text` в словах — это куски
  исходной строки, склеенные обратно они **должны совпадать** с текстом строки
  (пробелы включительно). Если не совпадают — баг парсера: разделение потеряло
  пробелы.

## Проверка

Тесты парсера — единственное, что не требует браузера. Держать их быстрыми
(десятки миллисекунд) и полными по краевым случаям.

## Чего не делать

- Не пытаться «угадывать» тайминги там, где их нет (это задача alignment, а не
  парсера).
- Не тянуть для этого библиотеку ради 100 строк логики — парсер маленький и
  предсказуемый.
- Не нормализовать текст (не менять регистр, не убирать пунктуацию) — текст
  должен отображаться как в оригинале.
