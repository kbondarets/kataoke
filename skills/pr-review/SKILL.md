# Скилл: ревью пул-реквеста

## Когда нужен

Ты — ревьювер и получил PR на проверку. Всегда. Без исключений «тут же мелочь».

Полная процедура — `.clinerules/workflows/review.md`. Этот скилл — концентрат, чтобы
не потерять порядок и не увлечься вкусом.

## Порядок (не переставлять)

1. **Предмет ревью.** Что меняется, какая задача, сколько файлов и строк.
   Не начинать с файлов — начинать с diff и описания PR.
2. **`npm run check`.** Красный → вердикт «блокирует», дальше не идти. (Исключение:
   если поломка заведомо не из этого PR — указать в вердикте и продолжить.)
3. **Границы модулей.** Селектор сервиса вне адаптера, `core` знает про сервисы,
   UI ходит в сеть — блокирует.
4. **Синхронизация.** Позиция из медиа-элемента, интерполяция, seek/pause/rate,
   дрейф, лишние ре-рендеры.
5. **Оверлей.** Shadow DOM, изоляция стилей, позиционирование, SPA.
6. **Провайдеры.** Таймауты, валидация, кеш, ошибки по-русски.
7. **Тексты.** По-русски, без жаргона, с подсказкой.
8. **Тесты.** Есть, проверяют поведение, ветки ошибок, без сети.
9. **Правки `VISION.md` / правил / `agents/`** — согласованы с владельцем.
10. **Секреты и permissions.**
11. **Читаемость и бюджет строк.**

## Блокирующее (что нельзя сливать)

- красный `typecheck` / `test` / `build`;
- нарушение границ модулей;
- позиция из прогресс-бара, или текст расходится с музыкой;
- протечка стилей в/из Shadow DOM;
- внешний запрос без таймаута;
- утечка секрета;
- отсутствие теста на новое поведение (`core`, провайдеры — обязательно);
- реализация из списка «не делаем» (`VISION.md` §6): обход DRM, ML в клиенте,
  сервер в MVP;
- продуктовая/архитектурная правка без согласования с владельцем.

## Режим «только чтение»

- Инструменты правки недоступны, и это правильно. Не пытайся обойти: никаких
  `node -e`, heredoc, перенаправлений.
- Bash — только из белого списка (`npm run check`, `npm test`, `git diff/log/show/
  status/ls-files`, `gh pr diff/view`, `git fetch`).
- Последняя команда — `git status --short`. В вердикте строка о чистоте рабочей
  папки.

## Формат вердикта

```
Вердикт: блокирует / можно сливать с замечаниями / можно сливать

PR: <ветка> → main, файлов: N, строк: +A / −B
Задача: <одна строка>

БЛОКИРУЮЩЕЕ
- файл:строка — суть. Что сделать.

СУЩЕСТВЕННОЕ
- файл:строка — суть и чем грозит.

МЕЛОЧИ
- ...

Проверено: typecheck ✓ / тесты N/N / build ✓
Не проверено: <что не удалось проверить и почему>
Рабочая папка чистая: да
```

Без вступлений и похвал. Файлами и строками. При отсутствии замечаний —
`- (пусто)`.

## Тон и границы

- Замечание — про поведение и риски, не про вкус.
- «Мне не нравится имя переменной» — это мелочь, и только если имя правда
  неинформативно.
- Не требовать новых библиотек, фреймворков, «переписать по-нормальному».
- Не переписывать задачу. Странная постановка → вопрос владельцу в вердикте.
- Не блокировать из-за мелочей.

## Как быстро смотреть дифф

- Сначала `git diff --stat` — понять масштаб.
- Потом по файлам, начиная с тех, что в `core` и `adapters` (там цена ошибки
  выше).
- Пропускать lock-файлы и сгенерированное, если зависимости не менялись.
- Не читать файл целиком, если в diff небольшая правка — читать diff, а точечно
  файл только для контекста.
- Для «странного» места — `git log -p -- файл` не нужно; достаточно diff.

## Честность

- Не проверено — так и написать. «Не проверял в живом сервисе» — нормальный ответ.
- Не выдавать предположение за проверенный факт.
- Если PR трогает то, в чём ты не уверен (например, неясен формат ответа API) —
  это вопрос, а не выдуманное замечание.
