# Ведение задачи (для frontend- и backend-агента)

Один и тот же процесс для обеих ролей. Отличается только область работы
(см. `agents/frontend-architect.md` и `agents/backend-architect.md`).

---

## 1. Перед началом

- Прочитать `.clinerules/rules.md`, `STATE.md`, нужный раздел `VISION.md`.
- Сформировать понимание задачи: **что** меняется, **зачем**, **какие файлы**
  затронуты. Если неясно — спросить владельца до кода.
- Если задача требует переделки соседней области (фронт ↔ бэк) — сообщить об этом
  **до** начала работы, а не после.

## 2. Ветка

```
git checkout main
git pull
git checkout -b feature/<краткое-имя>
```

Префиксы: `feature/`, `fix/`, `chore/`.

## 3. Работа

- Один шаг — одна законченная вещь. Не смешивать рефакторинг и фичу в одном PR.
- Каждый шаг сопровождается проверкой: `npm run typecheck` (быстро) → после
  набора изменений `npm test` → в конце `npm run build`.
- Не отключать тесты и не «временно» ослаблять типы, чтобы сборка прошла.
- Не трогать чужие файлы «заодно» — это попадёт в дифф и усложнит ревью.

## 4. Проверка перед PR

```
npm run check
git diff --stat
```

- Три зелёные галочки: типы, тесты, сборка.
- Просмотреть собственный дифф целиком. Чаще всего именно там видно отладочные
  `console.log`, закомментированный код и случайные правки.

## 5. Коммиты

```
<тип>: <описание по-русски>
```

Типы: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`.
Мелкие, осмысленные коммиты. Не «wip», не «фикс».

## 6. Pull request

В описании PR обязательно:

```
## Что сделано
- ...

## Зачем
<ссылка на задачу / раздел VISION.md>

## Как проверено
- typecheck ✓
- тесты: <N> добавлено, <M> всего
- сборка ✓
- вручную: <что именно открыли и посмотрели, если применимо>

## Что не проверено
<честно, например: «на живом Яндекс Музыке не проверял — подписка не активна»>

## Риски
<если есть>
```

## 7. Ревью

- Передать PR ревьюверу (см. `.clinerules/workflows/review.md`).
- С блокирующими замечаниями — править в той же ветке, затем повторное ревью.
- Не спорить с ревьювером в коде. Несогласие по существу — вопрос владельцу.
- Слияние — только после «можно сливать» / «можно сливать с замечаниями».

## 8. После слияния

- Обновить `STATE.md`: что сделано, где, какие подводные камни появились.
- Если принято долгосрочное архитектурное решение — записать его в
  `STATE.md` → «Решения» (дата, решение, почему).
- Если задача выявила проблему в правилах — предложить правку правил владельцу,
  а не править их молча.
