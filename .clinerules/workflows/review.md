# Ревью pull request / merge request

Ревью делает **не автор правки**. Автор знает, что хотел сделать, и поэтому
бессознательно считает свой замысел очевидным. Свежий взгляд видит то, что автор
уже не видит.

Ревьюер проверяет **пул-реквест / мерж-реквест** (далее — PR), а не «вообще код в
репозитории». Предмет ревью — изменение и то, как оно встраивается в проект.

---

## Как запускать

1. Разработчик (frontend- или backend-агент) закончил задачу в ветке и открыл PR
   (или владелец говорит «готово»).
2. Запускается агент-ревьювер с задачей:

   > Проверь PR `<номер или ветка>` по `.clinerules/workflows/review.md`.

3. Ревьювер возвращает вердикт в формате ниже. Автор правит и просит повторное
   ревью **по тому же PR** — по тем же правилам.
4. Слияние — только после вердикта «можно сливать» и отсутствия блокирующих.

---

## Шаг 0. Определить предмет ревью

В первую очередь — что именно меняется:

```
git fetch --all
git diff --stat origin/main...HEAD
git log --oneline origin/main..HEAD
```

Если PR открыт в GitHub/GitLab и есть доступ — брать diff оттуда
(`gh pr diff <номер>` / список изменённых файлов из API). Если доступа нет —
работать по локальной ветке против `main`.

Затем **прочитать задачу**, которую PR закрывает (описание PR, issue, или
сообщение владельца). Ревью без понимания задачи превращается в придирки к стилю.

Отдельно зафиксировать:

- какие файлы изменены и сколько строк;
- есть ли изменения в `VISION.md`, `projectRules.md`, `.clinerules/` (такие правки
  проверяются отдельно и строже — см. шаг 8);
- есть ли бинарные и сгенерированные файлы в diff (`dist/`, картинки, lock-файлы —
  последние только если менялись зависимости).

---

## Шаг 1. Механические улики

```
npm run check
```

Три зелёные галочки обязательны: `typecheck`, `test`, `build`. Красный результат
закрывает ревью сразу — дальше можно не смотреть.

Если в проекте появится `npm run review` (статический анализ) — прогнать и его.
**Его вывод — не приговор, а начало разговора.** Найденное — это вопросы к автору,
а не список правок. Если сработало ложно — так и сказать.

---

## Шаг 2. Границы модулей (главное)

Правило: `core` не знает про сервисы; `adapters/<service>` — единственное место,
где есть DOM-селекторы конкретного сайта; `ui` не знает про селекторы и не зовёт
провайдеров напрямую; `content` только связывает.

Проверить по diff:

- Не просочился ли селектор Яндекс Музыки / YouTube за пределы
  `src/adapters/<service>/`?
- Не импортирует ли `src/core/` что-либо из `src/adapters/` или `src/ui/`?
- Не ходит ли `src/ui/` в сеть напрямую (минуя `providers`)?
- Не тянет ли `providers/<name>` адаптеры или UI?
- Нет ли в `src/content/` бизнес-логики, которая должна быть в `core`?

Нарушение границы — **блокирующее**. Ответ на вопрос «если завтра Яндекс Музыка
поменяет вёрстку — сколько файлов чинить?» должен быть «один».

---

## Шаг 3. Синхронизация и плеер

Это ядро ценности продукта, поэтому проверяется придирчиво:

- Позиция берётся из `<video>`/`<audio>.currentTime`, а не из прогресс-бара в DOM?
  Прогресс-бар как источник времени — **блокирующее**.
- Учтена ли интерполяция между опросами `currentTime` (через `performance.now()` и
  `playbackRate`)? Если нет — строка будет дёргаться; это **существенное**.
- Обработаны ли `play`, `pause`, `seek`, `ratechange`, `ended`, смена трека?
- Что будет при перемотке назад/вперёд на 5 минут? Что будет при паузе между
  строками? Что при повторном клике play?
- Нет ли «дрейфа»: сравнить позицию, которую выдаёт движок, с реальной через
  несколько минут воспроизведения (мысленно или тестом).
- Есть ли лишние ре-рендеры на каждый кадр, или перерисовка только при смене
  активной строки/слова?

Любой путь, где время «расходится» с музыкой, — **блокирующее**: это ровно та боль,
которую продукт должен закрывать.

---

## Шаг 4. Оверлей и Shadow DOM

- Рендер идёт в shadow root, а не в `document.body` без изоляции? Протечка стилей
  в страницу или из страницы — **блокирующее**.
- Не ломается ли позиционирование при ресайзе, скролле, смене раскладки?
- Переживает ли оверлей переход между треками без размонтирования?
- Перехватывается ли SPA-навигация (`history.pushState`/`replaceState`,
  `MutationObserver`), чтобы смена трека не требовала перезагрузки?
- Не перекрывает ли оверлей важные элементы плеера (кнопки управления) на
  целевых разрешениях? Исходное положение не должно мешать пользоваться плеером.
- Нет ли обращений к странице вне `src/adapters/`?

---

## Шаг 5. Провайдеры и сеть

- У каждого внешнего запроса есть **таймаут**? Без таймаута — **блокирующее**.
- Что увидит пользователь, если провайдер вернул 500 / таймаут / пустой результат /
  кривой JSON? Текст по-русски и по делу?
- Не появляется ли «вечная загрузка»?
- Ответ внешнего API валидируется до использования (`unknown` → проверка → тип), а
  не приводится через `as`?
- Кеш есть и используется? Ключ кеша включает трек и длительность?
- Нет ли запросов на каждый кадр/каждую секунду?

---

## Шаг 6. Пользовательские тексты

Владелец не читает код — он читает интерфейс.

- Все новые сообщения — по-русски, без технического жаргона (`undefined`,
  `ECONNRESET`, `500`)?
- Понятно ли, что делать дальше («Попробуйте ещё раз», «Проверьте соединение»)?
- Нет ли английских строк в UI?
- Состояние «текст не найден» объяснено и не выглядит как ошибка приложения?

---

## Шаг 7. Тесты

- Новое поведение покрыто тестом?
- Тест проверяет **поведение**, а не реализацию? (Тест, который ломается от
  переименования функции, — плохой тест.)
- Проверены ли ветки ошибок, а не только счастливый путь?
- Нет ли теста, который всегда зелёный (нет `assert` или проверяет константу)?
- Тесты не ходят в сеть?

Отсутствие теста на новую ветку ошибки — **существенное** замечание.

---

## Шаг 8. Правки документации и правил

Если PR меняет `VISION.md`, `projectRules.md`, `.clinerules/` или `agents/`, это
проверяется отдельно:

- Правка согласована с владельцем? Продуктовые решения без его визы — **блокирующее**.
- Не удалена ли запись в «Решения, зафиксированные» без объяснения?
- Не противоречит ли новая правка другим разделам того же документа?

---

## Шаг 9. Секреты и данные

- В бандл/логи/тесты/git не попали ключи, токены, `.env`?
- В логах нет истории прослушивания пользователя?
- Permissions в `manifest.json` не расширены без необходимости? Новый домен в
  `host_permissions` — **существенное** (объяснить, зачем).

Утечка секрета — **блокирующее**, без обсуждений.

---

## Шаг 10. Читаемость

- Имена говорят, что вещь делает?
- Комментарии объясняют **почему**, а не «что»?
- Нет ли мёртвого кода и закомментированных блоков?
- Файл не разросся сверх бюджета (250 / 400 строк)?
- Нет ли случайных изменений (форматирование чужого файла, переставленные импорты)?

---

## Строгий режим: только чтение

Ревьюер работает **только на чтение**. Это не рекомендация, а проверяемый запрет.

### Разрешённые инструменты (белый список)

- `read_files` — чтение файлов;
- `search_codebase` — поиск по коду;
- `fetch_web_content` — только для проверки документации внешнего API, если PR его
  использует;
- `run_commands` — **только** для следующих команд:
  - `npm run check`
  - `npm run typecheck`
  - `npm test`
  - `npm run build`
  - `npm run review` (если появится)
  - `git status --short`
  - `git diff`
  - `git diff --stat`
  - `git log`
  - `git show`
  - `git ls-files`
  - `git fetch` (без слияния, только чтобы обновить `main` для diff)
  - `gh pr diff`, `gh pr view` (только чтение)

Любая другая команда через `run_commands` — запрещена.

### Запрещено категорически

- Создавать, изменять, удалять и переименовывать **любые** файлы в репозитории.
  Запрещены: `editor`, `Write`, `Edit`, `Set-Content`, `Out-File`, `New-Item`,
  `Remove-Item`, `move` и любые аналоги.
- Запускать: `git add`, `git commit`, `git checkout` ветки, `git restore`,
  `git stash`, `git reset`, `git merge`, `git push`, `npm install`,
  `gh pr merge`, `gh pr review --approve`.
- «Попутно исправлять» мелочь, которую заметил. Захотел исправить — значит это
  замечание в вердикте, а не правка в коде.
- Искать обходные пути. Если инструмент правки недоступен или запрещён — не
  писать файлы через `node -e`, `powershell`, heredoc, перенаправление вывода
  или любой другой способ. Обхода нет.

### Временные файлы

Логи долгих прогонов — только в системной временной папке (`%TEMP%`), с уникальным
именем. Удалять сразу после прочтения. В репозиторий не писать ничего, включая
логи.

### Обязательная самопроверка

Ревьюер **обязан** последней командой выполнить `git status --short`:

- Вывод пуст → написать в вердикте: `Рабочая папка чистая: да`.
- Что-то появилось → откатить изменения командами `git checkout -- .` и
  `git clean -fd` в **том же прогоне**, затем повторить `git status --short` и
  написать: `Рабочая папка чистая: да (после отката)` плюс перечислить, что
  пришлось откатить.
- Никогда не заканчивать прогон с грязной рабочей папкой.

## Формат ответа ревьюера

Коротко и по делу. Без похвал — они не помогают.

```
Вердикт: блокирует / можно сливать с замечаниями / можно сливать

PR: <ветка> → main, файлов: <N>, строк: +<A> / −<B>
Задача: <одна строка, что закрывает PR>

БЛОКИРУЮЩЕЕ
- src/...:42 — <что не так>. <что сделать>.
- (пусто, если нет)

СУЩЕСТВЕННОЕ
- src/...:88 — <что не так и чем грозит>.

МЕЛОЧИ
- ...

Проверено: typecheck ✓ / тесты N/N / build ✓
Не проверено: <например, «поведение в живом Яндекс Музыке — нет доступа»>
Рабочая папка чистая: да
```

Правила вердикта:

- **Блокирует** — есть хотя бы одно замечание из списка блокирующих.
- **Можно сливать с замечаниями** — блокирующих нет, существенные есть.
- **Можно сливать** — только мелочи или ничего.

Ревьюер **не имеет права** менять вердикт «можно сливать» на «блокирует» из-за
вкуса. Вкус — не замечание (см. «Чего ревьюер НЕ делает»).

---

## Чего ревьюер НЕ делает

- **ЗАПРЕЩЕНО править код любым способом.** Ревьюер возвращает только текст
  вердикта. Нашёл — описал файлом и строкой. Правит автор.
- **Не спорит о вкусе.** «Мне нравится другой отступ» — не замечание.
- **Не требует нового фреймворка или библиотеки.** Стек зафиксирован в `AGENTS.md`
  и `VISION.md`.
- **Не переписывает задачу.** Если задача поставлена странно — это вопрос
  владельцу, а не повод сделать по-своему.
- **Не блокирует из-за мелочей.** Мелочи идут в отдельный список и не мешают
  слиянию.
- **Не выдумывает проблемы.** Если не проверил — пишет «не проверено», а не
  «вероятно, сломано».

---

## Когда ревью можно пропустить

Почти никогда. Исключения:

- правка только текста документации, не затрагивающая `VISION.md` и правила;
- правка только стилей без изменения логики — и то, если это не ломает вёрстку
  (проверяется глазами).

Всё остальное — через ревью. Даже «одна строчка»: именно одна строчка чаще всего
и ломает.
