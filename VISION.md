# Kataoke — замысел продукта

> Рабочее название: **kataoke** (опечатка от karaoke, ставшая фишкой).
> Нормальное название придумаем позже — см. раздел «Нейминг».
> Статус документа: черновик v1, зафиксирован 2026-11-13.

---

## 1. В одном абзаце

**Kataoke** — расширение для браузера, которое показывает синхронизированный с воспроизведением текст песни (караоке-стиль) поверх **любого** музыкального сервиса: Яндекс Музыка, Spotify, YouTube Music, YouTube. Боль, которую закрываем: слышишь классную песню, хочешь подпеть — а текста нет, он не тот, или он «где-то в гугле». Мы даём текст здесь и сейчас, строка за строкой под текущий фрагмент, за 1–2 клика.

Ключевая идея архитектуры: **не привязываться к сервису**. Есть одно ядро, которое умеет «знать, что играет» и «рисовать текст». Каждый сервис подключается через маленький адаптер.

---

## 2. Целевой пользователь и сценарий

**Пользователь:** человек, слушающий музыку в вебе, который подпевает или хочет понимать текст.

**Сценарий «здесь и сейчас»:**
1. Сидит в Яндекс Музыке, играет трек.
2. Открывает расширение (иконка / хоткей / плавающая кнопка на плеере).
3. Видит текст, который подсвечивается в такт музыке.
4. Может переключить «караоке-режим» (крупный текст по словам), перемотку, скрыть панель.

**Что болит сейчас:**
- В Яндекс Музыке текст есть не всегда, и он не всегда правильный.
- В YouTube Music текстов может не быть вовсе.
- Гуглить текст в отдельной вкладке — медленно и неудобно, теряется синхронизация.
- Даже когда текст есть, он не «бежит» по словам, как в настоящем караоке.

---

## 3. Продуктовые принципы (не нарушать без явной причины)

1. **Один оверлей — все сервисы.** Ядро про сервисы ничего не знает. Логика сервиса — только в адаптере.
2. **Мгновенный отклик.** Пользователь никогда не должен ждать «генерации». Сначала показываем всё, что умеем показать сразу (хоть просто текст), потом улучшаем в фоне.
3. **Точная синхронизация — это фича №1.** Строки должны попадать в музыку, а не «примерно бежать».
4. **Кеш — это экономика.** Один трек считается один раз, дальше отдаётся всем из кеша. Нейросети — только для «хвоста» редких треков.
5. **Юридическая осторожность с первого дня.** Никаких обходов DRM, никаких модификаций чужого аудио. Данные (тексты) — из легальных/открытых источников, с пониманием risks.
6. **MVP маленький.** Расширение, один сервис, один источник текстов, ноль нейросетей. Сначала доказываем, что синхронизация вообще приятна в использовании.

## 4. Архитектура (важная часть замысла)

### 4.1 Слои

```
┌─────────────────────────────────────────────────┐
│  UI: оверлей (Shadow DOM) — React/Preact        │
│  - строка / караоке по словам / настройки       │
└─────────────────────────────────────────────────┘
                       ▲
┌─────────────────────────────────────────────────┐
│  Core: Sync Engine                              │
│  - текущая позиция (качественная), дрейф, seek  │
│  - таймлайн LRC/k-word → активная строка/слово  │
└─────────────────────────────────────────────────┘
        ▲                               ▲
┌────────────────────┐   ┌──────────────────────────────┐
│ PlayerAdapter × N  │   │ LyricsProvider × M           │
│ - Yandex Music     │   │ - LRCLIB (sync + plain)      │
│ - YouTube          │   │ - (v2) свой кеш/бэкенд       │
│ - Spotify (v2)     │   │ - (v2) forced alignment       │
│ - YT Music (v2)    │   │ - (v3) лицензионная база     │
└────────────────────┘   └──────────────────────────────┘
```

### 4.2 Контракты (черновики, для будущей реализации)

```ts
// Адаптер сервиса
interface PlayerAdapter {
  id: string;                                     // 'yandex-music'
  matches(url: string): boolean;
  getTrack(): TrackInfo | null;                   // { title, artist, album, durationSec, sourceId }
  getPositionSec(): number | null;                // из <video>/<audio>.currentTime
  isPlaying(): boolean;
  getPlaybackRate(): number;
  on(event: 'trackchange' | 'play' | 'pause' | 'seek' | 'ratechange', cb: () => void): () => void;
  destroy(): void;
}

// Источник текста
interface LyricsProvider {
  id: string;
  lookup(track: TrackInfo): Promise<LyricsResult | null>; // { kind: 'plain' | 'lrc' | 'word', lines }
}
```

### 4.3 Синхронизация (суть, а не только «читать currentTime»)

- Позиция берётся из медиа-элемента (`<video>`/`<audio>`) через `currentTime`, а **не** из прогресс-бара в DOM.
- `currentTime` в браузере обновляется «кусками», поэтому **интерполируем** позицию между опросами: `pos ≈ lastKnownTime + (performance.now() - lastSampleWall) / 1000 * playbackRate`.
- Реагируем на `play`, `pause`, `seek`, `ratechange`, `ended`, смену трека.
- Рендер — `requestAnimationFrame`-цикл, но **подсветка обновляется только при смене активной строки/слова** (иначе лишние ре-рендеры).
- Небольшой визуальный lead-in (опережение подсветки на ~80–120 мс) — так «на глаз» синхроннее, потому что человек читает заранее и рисует вперёд.

### 4.4 Оверлей

- Рендерим в **Shadow DOM**, чтобы CSS сайта (Яндекс/Spotify) не ломал наш UI и наоборот.
- Позиция над медиа-плеером: `position: fixed` + `ResizeObserver` на плеере, пересчёт при скролле/ресайзе/переходе по SPA.
- Навигация SPA: `MutationObserver` + `history.pushState`/`replaceState` перехват, чтобы ловить смену трека без перезагрузки страницы.

## 5. Источники текстов и синхронизации

| Источник | Что даёт | Плюсы | Минусы |
|---|---|---|---|
| **LRCLIB** (lrclib.net) | LRC (sync) + plain, открытый API | Бесплатно, много `.lrc`, можно ходить в код | Не всё покрыто, качество разное |
| Musixmatch API | Текст + sync | Лучшее качество и покрытие | Платно на объёмах, жёсткие правила, лицензия для коммерции — отдельно |
| Genius | Plain text | Огромная база, популярность | Без таймингов, API закрыт для новых, есть неофициальный |
| Deezer / Spotify | Текст (в приложении) | Есть в интерфейсе | Синхронизированный текст наружу почти не отдают |
| **Своя генерация таймингов** | LRC/k-word из plain-текста | Покрываем «хвост» | Нужен сервер + нейросеть (v2) |

**Стратегия по умолчанию (v1):** спрашиваем LRCLIB. Есть sync — показываем караоке. Есть plain — показываем текст, синхронизированный хотя бы построчно (или просто по центру, без подсветки по времени). Нет ничего — честно говорим «текст не найден», даём ссылку «найти вручную/сообщить».

### 5.1 Нейросети: где они нужны (и где нет)

- **Нужны:** *forced alignment* — когда есть текст, но нет таймингов. Модели: Whisper / WhisperX / stable-ts / ctc-forced-aligner. Извлечение вокала (MDX-Net / Demucs / UVR) перед alignment сильно повышает точность.
- **Важно:** alignment по **известному** тексту надёжнее «распознавания с нуля» — Whisper на музыке галлюцинирует (пропускает/додумывает строки).
- **Не нужны (в v1):** LLM для поиска трека, матчинга названий — справляется fuzzy-поиск (нормализация `feat.`, `remaster`, `radio edit`, trigram).
- **LLM (GPT/Claude)** — только для доп. фич (перевод, разметка куплет/припев, объяснение строки), не для ядра.

## 6. Что сознательно НЕ делаем (и почему)

### 6.1 «Приглушить вокал, оставить музыку» — вычеркнуто из MVP

Причин две, и обе — стоп-сигнал:

1. **Технически невозможно** на целевых сервисах. Яндекс Музыка / Spotify / YT Music отдают аудио через **DRM (Widevine/EME)**. Расширение не получает доступа к аудиопотоку → нет PCM → нельзя ни разделить стемы, ни ослабить вокал. `createMediaElementSource` на DRM-аудио вернёт тишину/ошибку.
2. **Юридически опасно.** Получение обработанного аудио из DRM-контента = обход защиты (отдельный состав в РФ и в ЕС/США), плюс derivative work с защищёнными правами. При монетизации — прямой риск.

**Что остаётся в копилке на потом:** караоке-микс возможен только в **собственном плеере** (свои аудиофайлы / легальный стриминг / доменная музыка). Это отдельный продукт, не расширение поверх чужих сервисов. Идею не выкидываем, но в скоуп расширения — нет.

### 6.2 Другие вещи вне MVP

- Android-версия (второй этап, см. раздел 8).
- Свой каталог текстов / лицензионная база (нужна для легальной монетизации, но не для MVP).
- Аккаунты и синхронизация настроек между устройствами.
- Мультиязычный интерфейс и переводы.

## 7. Выбор технологий и объяснение «почему»

> Поскольку пользователь не знаком с TS/Preact, ниже — объяснение на пальцах.

### 7.1 TypeScript

**Что это:** JavaScript + типы. Типы — это «подписи», которые говорят: «эта функция принимает строку, возвращает число». Перед запуском (при сборке) TypeScript проверяет, что типы сходятся; если нет — подчёркивает ошибку прямо в редакторе.

**Почему именно для этого проекта:**
- **Мультисервисность.** У нас контракты `PlayerAdapter` и `LyricsProvider`. Каждый новый сервис — новые поля, новые форматы. TypeScript ловит, что новый адаптер реализует все нужные методы и возвращает нужные поля — до того, как это упадёт в браузере у пользователя.
- **DOM-тряска.** Мы лезем в чужой DOM («найди этот плеер, вытащи `currentTime`»). Такие места ломаются внезапно и молча. Типы + явные проверки на `null` заставляют обрабатывать «а это поле не нашлось» — иначе расширение просто перестанет работать на конкретной странице.
- **Синхронизация со временем.** Тайминги в миллисекундах, проценты, секунды — легко перепутать. Тип-алиасы (`Seconds`, `Milliseconds`) и строгие правила уменьшают класс ошибок «на 1000 умножил не там».
- **Команда и долгосрочность.** Проект задуман как надолго (см. монетизацию). TS — фактический стандарт в расширениях и в продуктовой разработке; код читаемее, рефакторинг безопаснее.
- **Без накладных расходов на старте.** TS компилируется в обычный JS, браузер его не видит. Совместимость Chrome Web Store / Firefox — без вопросов.

**Что это НЕ:** не фреймворк, не «замена JS». Это тот же JS, но с проверкой типов на этапе сборки.

### 7.2 Preact (а не React)

**Что это:** React — самая популярная UI-библиотека (компоненты, состояние, реактивный рендер). Preact — её **совместимый, но очень лёгкий** аналог: тот же API компонентов и хуков, но ~3 КБ вместо ~45 КБ.

**Почему Preact именно для расширения:**
- **Размер.** В расширениях минимализм критичен — и код в web store скачивается быстрее, и парсится мгновенно. 3 КБ vs 45 КБ — это буквально разница «оверлей появился сразу» / «подожди».
- **API совместим с React.** Если завтра захочется React (например, появятся сложные части с React-специфичными библиотеками) — миграция почти без переписывания, через `preact/compat`.
- **Shadow DOM.** Preact прекрасно рендерится в shadow root — ровно наш случай (п. 4.4).
- **Альтернатив нет смысла:** чистый DOM (vanilla) — это руками собирать состояние и реактивность, дольше и баговее; Svelte/Vue — рабочий вариант, но экосистема/онбординг/совместимость у React-стека выше; Angular/Lit — перебор для оверлея.

**Итог:** TypeScript + Preact = быстрая разработка, крошечный бандл, безопасный рефакторинг и совместимость с миром React. Это «стандартный дефолт» для подобных расширений, а не экзотика.

### 7.3 Остальной стек (минимум, для скелета)

- **Manifest V3**, content scripts + service worker.
- Сборка: **Vite** (+ плагин/шаблон для MV3) — стандарт для расширений.
- Бандл: **WXT** (обёртка над Vite для расширений) — опционально, удобно, но можно и на голом Vite. Решим на этапе инициализации.
- Стили: CSS Modules / обычный CSS в Shadow DOM (без Tailwind на старте, чтобы не тащить лишнего).

## 8. Платформа: расширение vs Android

Выбрано **расширение (Chrome/Edge/Firefox, MV3)**. Причины:

| Критерий | Расширение | Android |
|---|---|---|
| Доступ к плееру | Легко, через DOM/медиа-элемент | Сложно, часто через Accessibility Service — нестабильно |
| Скорость до MVP | 2–4 недели | 1–2+ месяца |
| Дистрибуция | Chrome Web Store / AMO | Play Store, ревью дольше |
| Монетизация | Проще (внешние платежи, лицензии) | Google Play Billing, комиссия 15–30% |
| Покрытие кейса | Все перечисленные сервисы в вебе | Только при наличии MediaSession (не везде) |

Android — **второй этап**, и только через `MediaSession`/`NotificationListenerService`, либо как отдельный «караоке-плеер» со своим аудио. Не в MVP.

## 9. Сервер: нужен ли, сколько стоит, как минимизировать

**Для MVP сервер не нужен вообще.** Всё работает на клиенте:
- оверлей + sync engine — в браузере;
- тексты — напрямую с LRCLIB (бесплатный API);
- кеш — в `chrome.storage` (индекс по `трек+длительность`, храним только привязки к ID, не текст целиком — чтобы не нарушать лицензию LRCLIB).

**Сервер понадобится на v2**, когда добавим forced alignment (Whisper) — это тяжёлые модели, в браузере их не погоняешь.

### 9.1 Реальные деньги: не надо платить за простой

Главная ошибка в планировании — считать GPU по тарифу «круглосуточный инстанс».
Нам не нужен постоянно работающий сервер. Alignment нужен **урывками**: на трек
уходит несколько секунд, и **один раз** в жизни трека. Платить за 720 часов
пустого GPU — это и есть те «сотни долларов», которых не надо.

| Вариант | Что это | Стоимость |
|---|---|---|
| **MVP** | ничего, всё в браузере | **0 ₽** |
| **Офлайн на своём ПК** | батч-обработка популярных треков ночью, результат в общую базу | **0 ₽** (электричество) |
| **GPU по запросу** | включил на час, обработал 30–60 треков, выключил | **$1–10 в месяц** при старте |
| **CPU-инференс на VPS** | `whisper.cpp` / ONNX, медленнее (минуты на трек), без GPU | **$5–20** (VPS за $5–10) |
| Managed API для alignment | если появится нормальный сервис | по факту минуты обработки |

**Главная экономика — кеш.** Alignment считается один раз на трек и отдаётся всем
пользователям из общей базы. 99% прослушиваний — популярные треки, у которых
тексты уже есть в LRCLIB. Нейросеть нужна только для «хвоста» (новинки, редкие
треки, локальные исполнители). Поэтому стоимость на пользователя стремится к нулю,
а «сервер» на старте — это вообще ноутбук владельца.

**Практический план по серверу:**

1. **MVP** — сервера нет.
2. **Появились «не найденные» треки** — обработать их офлайн на своём ПК, залить
   результаты в статический файл/репозиторий. Стоимость — 0 ₽.
3. **Кеш перестал успевать** — почасовой GPU по требованию, с очередью и
   автозавершением. Бюджет начинается с единиц долларов.
4. **Реальные пользователи и деньги** — только тогда разговор про постоянный
   сервер и бюджеты в десятки долларов.

Порог перехода: смотрим не на «сколько пользователей», а на **долю треков без
текста** и на то, сколько таких запросов приходит в сутки.


### 9.2 Что важно знать про Яндекс Музыку (основной сервис)

- Главный тест-кейс, поэтому адаптер должен быть самым вылизанный.
- Музыка идёт через HTML медиа-элемент, позиция доступна через `currentTime`.
- Название трека/артиста удобнее брать из внутреннего состояния плеера или из URL/метаданных на странице, но стабильного публичного API нет — **придётся наблюдать за DOM и подстраиваться**. Это хрупко: при редизайне Яндекс Музыки адаптер может сломаться. Закладываем это как риск и стараемся опираться на несколько источников (URL, метаданные, DOM-элементы).

## 10. Монетизация (замысел, без деталей реализации)

Честно: **за текст песни люди не платят**. Платят за удобство и уникальность.

1. **Freemium.** Базовый караоке бесплатно; премиум — k-word синхронизация, темы/шрифты, PiP-плеер, офлайн-кеш, приоритет генерации редких треков.
2. **Языковое обучение.** Текст + перевод + разбор слов + повтор фраз — ниша, где платят.
3. **Создатели контента.** Браузерный source для OBS (стрим-караоке) — готовый рынок.
4. **Мерч/донат** — вторично, не как бизнес-модель.

**Ключевое ограничение:** для коммерческой монетизации потребуется **легальная база текстов** (Musixmatch/LyricFind — переговоры и деньги). В MVP это не блокер (LRCLIB + пользовательские привязки), но **публичный бизнес без лицензии — риск**. Это надо держать в уме с самого начала.

**Аудитория:** начинаем с русскоязычной (проверка гипотезы на себе), но **целимся в глобал** — там рынок монетизации. Русскоязычный рынок — для валидации, не для дохода.

## 11. Конкуренты и отличие

- **BetterMusic** и подобные — работают за счёт собственной базы sync-текстов (сервер + оверлей). Слабые места: покрытие редких треков, точность по словам.
- **Spotify** встроил синхронный текст — но только у себя и только там, где есть.
- **Lyricify / Lyricate / Spicetify+плагины** — ниша, но доказывают спрос.

**Наше отличие (задумка):**
1. Мульти-сервисность (один оверлей — все плееры).
2. Точность по словам (alignment для «хвоста»).
3. Скорость «здесь и сейчас» — даже для только что вышедших треков (показываем plain сразу, догенерируем sync в фоне).

## 12. План по этапам

**MVP — «прочувствовать синхронизацию» (2–4 недели)**
- MV3-расширение + оверлей в Shadow DOM (TypeScript + Preact).
- **Основной адаптер: Яндекс Музыка** (главный кейс, тестируем на себе). Доп. адаптер: YouTube (проще, для кросс-сервисной проверки ядра).
- Источник: LRCLIB. Есть LRC — караоке по строкам; нет — plain-текст по центру; нет вообще — понятная надпись и ссылка.
- Синхронизация: `currentTime` + интерполяция + реакция на play/pause/seek/rate/trackchange.
- Без сервера, без нейросетей, без монетизации.

**v2 — «точность и покрытие»**
- Сервер + очередь + WhisperX alignment по запросу, бессрочный кеш (Postgres/S3).
- Отдача k-word в клиент, подсветка по словам.
- Spotify / YT Music адаптеры (только текст/оверлей — из-за DRM).
- VPS-бюджет: начать с CPU-инференса, GPU — при необходимости.

**v3 — «продукт на продажу»**
- Перевод, PiP, OBS-оверлей, темы.
- Решение лицензии контента до публичного монетизации-релиза.
- Глобальная аудитория и оплата.

## 13. Нейминг (идеи, ничего не финализируем)

Рабочее `kataoke` — забавная опечатка, которую **можно использовать как один из вариантов** (запоминается, есть история). Другие направления:

- **Прямые:** `LyricOverlay`, `KaraOverlay`, `SubTune`, `VerseFlow`, `SingOver`.
- **Про универсальность:** `AnyLyrics`, `Anywhere Lyrics`, `MultiKaraoke`.
- **Про синхронизацию:** `SyncLine`, `WordBeat`, `BeatText`, `OnBeat`.
- **Про «пой сейчас»:** `SingNow`, `Подпевай` (для русского рынка), `UnderSing`.
- **Забавные/мемные:** `Kataoke` (игра слов katakana/karaoke), `Kareoke`, `Sing-a-long`.

Проверить на этапе выбора: свободны ли домен и имена в Chrome Web / Play Store / app stores, нет ли коллизий с существующими расширениями.

## 15. Решения, зафиксированные (summary)

- Платформа: **расширение браузера (MV3)**, основной сервис — **Яндекс Музыка**.
- Качество синхронизации — главная ценность; мульти-сервисность — через адаптеры.
- Стек: **TypeScript + Preact + Vite**, Shadow DOM оверлей.
- MVP: **без сервера и без нейросетей**, тексты из **LRCLIB**.
- «Приглушить вокал» — **вне скоупа** (DRM + юридика).
- Аудитория: русскоязычная для валидации, глобальная для монетизации.
